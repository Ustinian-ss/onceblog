> 手上攒了十几个 Provider、几十个模型、若干个 Key，想知道「现在到底哪些还能用、哪个快、哪个支持流式」—— 手工挨个点太慢，于是写了个工具把它们一次性测完并导出 CSV。

<!--more-->

## 一、要解决的问题

只要同时用过几家 OpenAI 兼容服务，就会遇到这些麻烦：

- 模型清单变化快，昨天还能用的今天报 404
- 同一个模型在不同 Provider 上延迟差好几倍
- 有些端点号称支持流式，实际返回一次性全量结果
- Key 有额度和冷却，撞上限流后不知道该换哪一个

这些问题的共同点是：**都只能靠实测回答，而手工测太慢**。`model-probe` 就是把这个过程自动化。

## 二、三个子项目

| 目录 | 用途 |
|---|---|
| `model-tester/` | 核心：PySide6 桌面端，批量测可用性 / 延迟 / 流式支持 |
| `key-manager/` | 多 Key 调度与轮换：轮询 / 加权 / 失败冷却 / 自动切换 |
| `data-scripts/` | 针对历史数据快照的一次性聚合分析脚本 |

项目原名 `nvidia-tools`，2026-09 改名 `model-probe`，更贴合「批量探测连通性」这个定位。

## 三、model-tester：测什么

### 三个维度

1. **可用性** —— 请求是否成功返回，以及返回结构是否符合预期（有些端点 HTTP 200 但 body 里是错误对象）
2. **延迟** —— 区分首 token 延迟和总耗时，这两个指标对交互式应用的意义完全不同
3. **流式支持** —— 是否返回 SSE 增量，还是攒完一次性吐出来

### 并发与多 Provider

GUI 用 PySide6 写，测试任务丢进线程池并发执行，多 Provider、多模型可以一起跑。界面实时刷新状态，跑完一键导出 CSV。

用 GUI 而不是纯 CLI，是因为这个工具的使用场景是「打开、扫一眼、挑一个能用的」——表格形式的实时状态比滚动日志直观得多。

## 四、key-manager：Key 不该以明文出现

多 Key 调度支持**轮询 / 加权 / 失败冷却 / 自动切换**四种策略组合。

但更想说的是两个安全上的决定：

**第一，列出 Key 时默认只显示 SHA256 指纹，不显示明文。**

```bash
python rotate_keys.py list    # 列出 Key（默认仅 SHA256 指纹）
python rotate_keys.py audit   # 指纹对照控制台
```

这样即使有人截屏、录屏、或者把终端输出贴进聊天窗口，也不会泄露凭据。需要人工核对时，用 `audit` 拿指纹去控制台比对。

**第二，`.env` 轮换脚本 + 运维 RUNBOOK。**

轮换这件事容易「只在脑子里记得怎么做」，一旦隔几个月再做就得重新踩一遍坑。所以把步骤写成 RUNBOOK，脚本负责执行，文档负责人脑记忆之外的恢复。

## 五、打包成单文件 exe

```powershell
.\build_exe.ps1    # 产物 dist\NvidiaModelTester.exe，内置模型清单
```

用 PyInstaller 打成单文件，**把模型清单一起内置**，这样拿到 exe 的人不需要额外配置就能直接开测。

## 六、写完之后的几点体会

- **失败冷却必须有**。并发测试很容易把某个 Provider 打到限流，然后后面所有请求全失败 —— 看起来像「服务挂了」，其实是自己打上去的。给失败的 Key 加冷却时间，结果才可信。
- **指标要分开看**。首次延迟低但总耗时长的模型，适合流式交互；总耗时短但首字慢的，适合批处理。混在一起排序会误导选型。
- **默认值要考虑泄露风险**。工具类程序经常会出现在截图、日志、issue 里，凡是默认输出就可能被公开，所以默认必须是安全的那一个。
